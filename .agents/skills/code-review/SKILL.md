# Проверка изменений

## Вход и полномочия

Получай цель/контракт, текущую роль и этап, разрешённую область, исходное состояние и фактическую среду. Метод определяет процедуру, не назначает роль, не расширяет ТЗ и не разрешает следующий этап. Выполняй только часть, доступную текущей роли; аналитик возвращает предложения текстом, тестировщик продукт не исправляет. Не запускай исполнителей самостоятельно.

Прочитай [обязательные правила](../../rules/INDEX.md) и профиль по объявленному в корневом AGENTS.md пути `project_profile`. Основной фокус: BASE-07–08, TEST-01/03–04/06/10 и все применимые группы. Остальные применимые нормы тоже действуют. Не используй отсутствующий учебный файл/сервис как обязательную зависимость. Недостающий обязательный вход или выход за границы верни координатору до записи.

## Процедура

1. Прочитай требование/ТЗ, реальные изменения и применимые правила/профиль. Установи область и состояние, к которому относится вывод.
2. Проследи наблюдаемое поведение, типы границ, валидацию, ответственность слоёв, ошибки и эффекты; для Python — аннотации/PEP 8, для async — I/O/await/отмену.
3. Проверь безопасность/логи/данные только для затронутых потоков. Сверь конфиги контроля и тесты с исходным состоянием: ослабление не скрывает дефект.
4. Для тестов проверь независимый оракул, реальные пути, полезные утверждения, подмены и пробелы. Наличие зелёного прогона не закрывает архитектурное нарушение.
5. Для замечания укажи AC/ID правила, место, воспроизведение или конкретный путь ошибки, ожидание, факт, влияние и минимальную правку.
6. Отличай обязательный дефект от пожелания. Не фиксируй произвольный стиль/абстракцию как блокер. Не исправляй продукт в режиме ревью.
7. Верни доказательства, команды и непроверенное. В панели сначала независимый отчёт, затем обсуждение; метод не создаёт четвёртого обязательного ревьюера.

## Результат

Передай текущей роли/координатору наблюдаемый результат, артефакты в разрешённых путях, основания решений и проверки со статусами passed/failed/not_run/not_applicable. Невыполненное не называй успешным; новые пути, контракт или обязательная зависимость требуют решения по ТЗ. Следующий этап и внешние действия метод не разрешает.
