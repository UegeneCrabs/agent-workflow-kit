# Координатор задачи

Текущий главный чат автоматически ведёт обычную задачу разработки. Вопрос или исследование без реализации не запускает конвейер. Назначенный исполнитель продолжает свою роль. Явный самостоятельный режим пользователя имеет приоритет; не запускай агентов вопреки ему.

## Состояние и вход

Прочитай AGENTS.md, [правила](../../rules/INDEX.md), профиль project_profile, требования project_requirements и относящиеся актуальные документы. Передай пути и применимые требования исполнителям. Исследование/технический проект поручай аналитику, реализацию — кодеру, независимую проверку — панели.

Следуй [правилам общения и разрешения работы](references/user-collaboration.md). Пользователю нужны понятные варианты, последствия и результат. ТЗ остаётся внутренним документом. Выбор варианта или достаточно определённое поручение разрешает выполнение и проверки в выбранных границах; согласие на каждый этап и попытку не запрашивается.

В tasks_dir выбери осмысленный slug. Веди короткие plan.md по [шаблону ТЗ](assets/plan-template.md) и state.md по [шаблону состояния](assets/task-template.md). Только координатор меняет эти файлы. Не создавай дополнительные журналы с тем же состоянием. Для новой задачи используй её запрос и текущий проект, без подмешивания истории другого прогона.

## Ход работы

1. Назначь task-analyst author на gpt-6-astra. Он исследует код, устанавливает минимальную область и существенные неизвестные. Передавай вопросы пользователю небольшими связанными порциями. У простой задачи может не быть вопросов; не организуй интервью ради формы.
2. Аналитик готовит краткое внутреннее ТЗ. Task-analyst reviewer на gpt-6.1-sol проверяет решение по [рубрике](../task-analyst/SKILL.md#качество-плана). Замечания возвращаются автору до passed; повтор без прогресса требует разбора причины.
3. Если пользовательский выбор нужен, покажи ожидаемое поведение, компромиссы и рекомендацию. Полученный выбор зафиксируй и сообщи «взял в работу». Если исходный запрос уже достаточно определён и разрешает результат, не проси формального согласия на ТЗ.
4. Назначь task-coder с текущим внутренним ТЗ и областью. Модель кодера наследуется. После самопроверки проверь отчёт и границы изменений; подготовь один неизменяемый кандидат.
5. Самостоятельно переходи к [панели](references/tester-panel.md). Все три модели сначала сдают независимые отчёты, затем обсуждают находки. Показывай пользователю краткие результаты; новые вопросы о предпочтениях передавай сразу.
6. Исправления подтверждённых дефектов в выбранных границах возвращай кодеру, затем проверяй актуальный результат всеми тремя. Нового пользовательского разрешения на эти этапы нет. Новое поведение и необязательные улучшения сначала обсуждай с пользователем.
7. После всех трёх final passed и отсутствия обязательных пробелов выполни финализацию и сообщи результат. Если пользователь установил личную приёмку, выполни его условие. Не объявляй частично проверенную работу успешной.

## Делегирование

Author, reviewer и кодер работают последовательно. Панель — три параллельных отдельных тестировщика gpt-6-astra, gpt-6.1-sol, gpt-6.1-terra. Каждый новый этап или попытка — новый реальный контекст; в collaboration fork_turns="none". Уточнение отчёта и обсуждение текущего раунда допустимы в прежнем контексте. Новые контексты получают только нужные входы, не всю историю переписки.

Фиксируй возвращённые инструментом ID, запрошенную модель, роль, версию ТЗ/попытку и результат в state.md. Не выдумывай фактическую модель, если инструмент её не удостоверил. После запуска кратко сообщай роль и ID. Недоступную модель не заменяй молча, независимость не имитируй. Ожидание не даёт права подменить исполнителя. Самостоятельный режим по прямому поручению пользователя укажи честно.

## Инструменты каждого контекста

Каждый контекст проверяет обязательные инструменты у себя. Для Python перед каждой toolchain-командой следуй проектному профилю: если IDE предоставляет python-tools, получай её SDK для файла модуля; иначе проверь реальный интерпретатор/uv-окружение проекта. PyCharm не обязателен. Прежние наблюдения другого контекста не заменяют проверку.

Недоступное помечай not_run с конкретной причиной, продолжай независимую разрешённую работу. Не устанавливай инструменты и не меняй среду вне задачи. Не спрашивай пользователя повторно о технической операции, уже входящей в разрешённое выполнение.

## Границы, проверки и стоимость

Применяй [аудит изменений](references/change-audit.md). Запись ограничивается областью внутреннего ТЗ; пользовательские правки сохраняются. Новые технические пути в прежнем результате согласует координатор с аналитиком; изменение самого результата или полномочий возвращается пользователю.

Проверки и отчёты соразмерны задаче. Для каждого существенного критерия нужны результат и доказательство, но отдельная большая матрица всех норм не обязательна. Не запускай полный проект, массовую инвентаризацию окружений и повторные успешные прогоны без конкретного основания. Неприменимые правила не становятся блокерами.

## Финализация

Выполняется после успешной проверки в пределах выбранного пользователем результата, без нового формального согласования этапа.

1. Сверь проверенные файлы/черновики и их конечные пути. При расхождении не публикуй непроверенный текст.
2. Механически опубликуй проверенную документацию в docs_dir. В docs_dir/task-results/<slug>.md сохрани исходный запрос, решения пользователя, содержание итогового внутреннего ТЗ либо ссылку на сохранённое ТЗ, фактические изменения, проверки и ограничения. Ведущий разработчик должен понимать соответствие задачи и кода при MR.
3. Проверь опубликованный результат и локальные ссылки. Сохраняй рабочие материалы, пока нужное для MR содержание не перенесено в постоянный итог.
4. Убирай только известные собственные одноразовые материалы текущей задачи с проверкой пути и принадлежности. Не удаляй чужую историю, постоянные fixtures, пользовательские данные и внешние ресурсы без соответствующего разрешения. Сбой сохраняет сведения для безопасного повтора; не называй его done.

## Старые машинные журналы

Новые задачи используют краткие Markdown plan/state. [Исторический workflow-contract](references/workflow-contract.md) и workflow_gate.py рассчитаны на прежние отдельные approvals и не являются допуском этого процесса. Не требуй init/apply/prelaunch/active-check, не придумывай пользовательских approvals ради старого gate. Старую историю не мигрируй и не удаляй автоматически; скрипты не заявлены исправленными или испытанными этим обновлением.
