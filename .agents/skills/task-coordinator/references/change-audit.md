# Аудит относящихся изменений

Координатор проверяет границы и сохранность пользовательской работы. Аудит соразмерен влиянию задачи и не заменяет проверку поведения. Пользовательские решения и разрешение работы — по [правилам общения](user-collaboration.md).

## До записи

Зафиксируй фактические исходные изменения и сбои в относящейся области, включая значимые игнорируемые/неотслеживаемые файлы. Выбери достаточный способ сравнения: diff и перечень путей, точечные хеши/копии важных конфигов либо снимок. Один git diff не покрывает всё игнорируемое, а полный обход окружений/кешей не обязателен для локальной правки.

Задай точные пути и поведение записи исполнителя. Учитывай реальные пути, родителей, symlink/junction, побочные записи форматтеров/генераторов, общий изменяемый ресурс. Сохраняй пользовательские изменения, не делай массовый reset/restore.

## После реализации и для панели

Сравни фактический вклад с областью и смыслом ТЗ. Проектные исходники, тесты, значимые конфиги и черновики документации входят в проверяемый результат. Для панели один актуальный кандидат; каждый пишет только свои артефакты.

Если в целевом проекте уже есть подходящий инструмент снимков, используй его реальные команды и объяви exclusions. Этот выпуск не требует создавать или устанавливать отдельный сканер ради обычной задачи. Снимок хранится вне сканируемого корня. Не запускай новый полный обход после каждой команды без конкретного основания. Для параллельной панели сравнивай объединение разрешённых каталогов; чужая разрешённая запись не приписывается соседу. Путь указывает предполагаемого владельца, не доказывает процесс-автора.

Различай содержательные изменения исходников/SDK/запуска и служебные счётчики/метрики среды. Незначимую метрику зарегистрируй с основанием; она сама по себе не означает нарушение пользовательского результата. Не скрывай под ней изменение всего конфигурационного файла. Не выдавай изменённые байты за прежний снимок. Неразобранное содержательное изменение останавливает зависимый переход, не оправдывает молчаливый rebaseline.

Проверяемый код/документы не меняются во время панели. Изменения возвращаются кодеру и проходят относящуюся актуальную проверку всех трёх; отдельное пользовательское разрешение нужно только при изменении результата/полномочий.

## Документы и завершение

Черновик → конечный путь docs_dir → идентичность проверенного текста. Проверяй факты/ссылки относительно конечного места. После успешной панели координатор публикует проверенный текст и сохраняет запрос, решения, итоговое ТЗ/ссылку и фактические изменения для MR.

Рабочий план не удаляется до сохранения его полезного содержания. Уборка затрагивает только известные собственные одноразовые материалы текущей задачи; проверь абсолютные пути, принадлежность и отсутствие неожиданного перехода по ссылке. Чужая история, постоянные fixtures, пользовательские данные и внешние ресурсы не входят автоматически в уборку. Для внешних ресурсов нужны соответствующие полномочия и отдельный учёт по проекту, когда они применимы.

Публикация/уборка — новые изменения, а не прежний хеш кандидата. При сбое сохраняй данные и выполненные действия для безопасного повтора. Не добавляй новые технические решения во время механической публикации.

## Совместимость

Старые машинные журналы относятся к истории конкретного проекта; [заметка о совместимости](workflow-contract.md) не является новым машинным протоколом; новые задачи не обязаны создавать ledger/approval events/finalization receipts старого gate. Не подделывай их и не мигрируй прошлые задачи автоматически. Сохраняй их исходные доказательства.
