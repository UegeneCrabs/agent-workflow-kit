# Качество переносимого набора

Следуй [общению с пользователем](../../task-coordinator/references/user-collaboration.md). Проверки соразмерны обновлению. Явное поручение без агентов/испытаний выполняется напрямую; не называй статическую проверку независимым поведенческим испытанием.

## Структура и согласованность

- Сохраняй пять основных навыков и15канонических методов по [каталогу](method-catalog.md), семь файлов правил и40стабильныхID. Вложенные validation fixtures не входят в число основных навыков.
- Изменённые SKILL.md имеют name/description и корректные относительные ссылки. Существующие metadata, dependencies и policy сохраняются; short_description25–64символа, default_prompt упоминает $имя-навыка.
- Общие инструкции не содержат названий/SDK/абсолютных путей исходного проекта. Корневой AGENTS содержит один маркерный блок и шесть объявленных путей, профиль/требования находятся вне .agents/.
- Роли и шаблоны согласованы: пользователю описание результата/вариантов, разработчику внутреннее ТЗ; выбранный результат разрешает реализацию/проверки/исправления/завершение. Версия или хеш сами по себе не требуют нового пользовательского согласия.
- Новые вопросы могут прийти от любой роли через координатора; техника исследуется, известные ответы сохраняются, дополнительные улучшения отдельно.
- Author Astra, reviewer Sol, coder inherited; три tester Astra/Sol/Terra независимы до3initial. РеальныеID/параметры не подменяются fixture.
- Новые plan/state — краткий Markdown. Legacy gate и [исторический контракт](../../task-coordinator/references/workflow-contract.md) не являются допуском; не создавать фиктивные approvals.
- В постоянном итоге для MR остаются запрос, решения, итоговое ТЗ/доступная ссылка, фактические изменения и проверки. Рабочий план не удаляется раньше сохранения этого содержания.

Выбранный профиль стека и версия библиотеки зафиксированы в проекте. В новом проекте применены только нужные модули, в существующем сохранены обнаруженные версии/команды. Локальная среда определяется без обязательного PyCharm.

## Выбор проверок

Для узкой правки инструкций проверь изменённые формулировки, frontmatter, ссылки и отсутствие противоречий в подключении/шаблонах. quick_validate системного skill-creator полезен для проверки структуры навыка при соответствующем объёме; его отсутствие не является доказательством поведения. Перед Python toolchain соблюдай python-tools и актуальную среду. Установки вне задачи нет.

Новые/изменённые исполняемые скрипты проверяются по применимым lint/type/поведенческим требованиям. Редактура Markdown не запускает по умолчанию всю регрессию процессных скриптов, массовую инвентаризацию сред или новое испытание набора навыков. Не повторяй успешный запуск без изменений/сбоя/конкретного сомнения.

При порученном испытании используй [сценарии](acceptance-scenarios.md) и [панель](../../task-coordinator/references/tester-panel.md). Ожидания выводятся из задачи, не передаются испытателю как готовые голоса. Наблюдаемое продолжение агента и реальные команды отличаются от проверки наличия слов.

Намеренно дефектные fixtures — объекты отрицательного испытания, не продукт. Не исправляй их ради зелёного и не освобождай под этим названием реальный новый код от норм.

Отчёт краткий: что изменено, реальные проверки, результаты/ограничения. Структурная проверка не доказывает UI discovery, запуск моделей или выполнение полного pipeline.
